# 全栈开发

## 共同规范

- 使用中文沟通、提问和交付。新增或修改代码时，同步补充或更新中文注释，说明业务目的或特殊处理的原因。保留准确的注释，删除因本次改动而过期的注释。
- 先理解现有代码和约定，明确目标与可观察的验收标准。关键不确定性会改变业务行为、接口契约或改动范围时，先询问再做相关改动。大型任务分阶段推进，汇报关键进展。发现明显风险或更简单的可行方案时，说明具体影响。
- 数据库排查和验证只执行只读 SELECT。执行前说明查询目的和可能影响的库、表或数据范围。禁止执行数据或结构变更，包括通过 ORM、迁移、种子脚本、测试脚本或应用入口间接触发的写入。需要变更时，仅提供 SQL 供用户确认后自行执行，明确标注涉及的表与字段及其业务含义，不使用外键约束。
- 测试、联调和设计验收产生的可重建截图、报告、录屏及临时文件统一放在仓库根目录的 `artifacts/`，不提交 Git。

## 按任务选择流程

- 实现、修复和故障排查使用下方最小改动流程。涉及页面或组件时读 [前端](references/frontend.md)，涉及 API、服务或数据访问时读 [后端](references/backend.md)。
- 审查指定的变更、PR、提交或文件，以及审计模块或全仓时，读 [代码审查与审计](references/review-audit.md)。只要求审查或审计时，交付只读报告。
- 盘点有标记的技术债时，读 [技术债盘点](references/debt.md)。只要求盘点时，交付只读清单。

## 最小改动流程

1. 从用户实际入口追踪到问题所在，检查受影响的调用方、既有测试和项目约定。修复共用逻辑的根因时，核对所有调用方依赖的行为。
2. 以完成验收所需的最小范围改动。先复用项目已有组件、服务、工具和测试方式，再考虑标准库或平台能力。保持仓库风格、校验和错误处理，避免无关功能、重构、依赖、配置和格式调整。保留现有调用方的行为，除非任务明确要求变更。
3. 涉及前后端时，先确认请求参数、返回字段、错误语义及兼容性，再沿调用链实现与联调。编写通用脚本时，沿用项目已有运行方式，用代表性输入和一个关键失败场景检查输出、退出码和必要的文件副作用。
4. 从页面、API 或脚本的正常入口验证实际行为，覆盖本次改动影响的正常场景和关键边界。会触发数据库写入的路径使用现有 mock 或测试替身。新增非平凡逻辑时，用一个聚焦的回归测试或自检覆盖关键行为。
5. 对有明确适用上限的简化，在相关代码旁用中文注释 `shortcut: <当前限制>，<何时升级>`。交付前核对 diff 和验收标准，用中文说明实际改动、验证结果、失败或跳过原因，以及仍需注意的实际风险。
